## Important source-derived authorization findings

1. **Kobo request-token concurrency — CRITICAL triage.** [KoboController.java:40](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/controller/KoboController.java#L40) declares mutable controller field `private String token`, [KoboController.java:57](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/controller/KoboController.java#L57) assigns it from `@ModelAttribute captureToken`, and later handlers use `token`. With ordinary Spring singleton controller scope, concurrent requests may overwrite request-scoped identity state. **Potential cross-request token mix-up**, not observed exploitation. All Kobo forwarding remains OFF until thread/request scoping fixed upstream or isolated and tested in an approved architecture.
2. **Nested book-file progress binding.** [ReadingProgressService.java:201](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/service/progress/ReadingProgressService.java#L201) loads book by request bookId; [ReadingProgressService.java:225](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/service/progress/ReadingProgressService.java#L225) updates `fileProgress.bookFileId` using a separately loaded file. In the reviewed source segment, no check ties the file's book ID to the currently eligible request book or its allowed library/content. Gateway must reject mismatched/nested IDs before forwarding any write. This applies also to App Progress delegation.
3. **KOReader book-hash entitlement.** [KoreaderService.java:80](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/service/koreader/KoreaderService.java#L80) authenticates KO sync user then resolves hash to a book and writes user progress. No current assigned-library/content eligibility check appears between those steps in the reviewed method. Reject stale/revoked/unassigned book hashes and prove full identity/tenant binding; user progress `findByUserIdAndBookId` alone is insufficient.
4. **Magic Shelf public-create privilege.** [MagicShelfService.java:50](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/service/MagicShelfService.java#L50) checks user ownership for existing shelf update/delete, but the new shelf branch flows into `toEntity` which sets `entity.setPublic(dto.getIsPublic())` ([MagicShelfService.java:100](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/service/MagicShelfService.java#L100)) without an explicit admin-only public shelf creation guard in the inspected service. Compare [ShelfService.java:42](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/service/ShelfService.java#L42), which explicitly checks admin on regular public shelf creation. Treat non-admin public Magic Shelf creation as **source-level authorization gap** pending an independent full-chain review.
5. **Kobo body-to-path entitlement.** [KoboController.java:157](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/controller/KoboController.java#L157) accepts `{bookId}` but for local IDs calls `saveReadingState(body.getReadingStates())`, while [KoboReadingStateService.java:82](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/service/kobo/KoboReadingStateService.java#L82) persists DTO entitlement IDs scoped to user. No source proof that every body entitlement equals the path book ID and has current book/content access.
6. **First-admin setup concurrency.** [SetupController.java:37](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/controller/SetupController.java#L37) guards public `POST /api/v1/setup` by checking whether any user exists before `provisionInitialUser`, but [UserProvisioningService.java:44](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/service/user/UserProvisioningService.java#L44) provisioning does not demonstrate an atomic one-time init admission lock relative to the controller precheck. This is a race-test requirement, not proof that more than one admin can be created.
7. **KO registration credentials/logging.** [KoreaderController.java:37](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/controller/KoreaderController.java#L37) returns 403 but logs full `userData`; [RequestLoggingFilterConfig.java:12](https://github.com/grimmory-tools/grimmory/blob/402e89b4452f8e2b17ab95f16c1621c003516cd2/backend/src/main/java/org/booklore/config/logging/RequestLoggingFilterConfig.java#L12) enables payload and header logging while `x-auth-key` and `x-auth-user` are not explicit excluded headers.
